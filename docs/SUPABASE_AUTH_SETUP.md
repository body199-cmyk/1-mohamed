# إعداد الدخول الآمن (AUTH-01) — توثيق وتحضير مستقل

**الحالة:** مكتوبة ولم تُختبر · **متوقفة بسبب عائق موضح** · لا تُعتبر اعتمادًا من المساعد.
**آخر مراجعة:** ٤ نوفمبر ٢٠٢٦ (BUILD-01 / الأجزاء المستقلة).

> هذه الوثيقة **لا تُنشئ مشروعًا سحابيًا ولا تُغيّر إنتاجًا ولا تُثبّت حزمًا**.
> هي تسجّل ما تحقّقنا منه رسميًا، وما هو ناقص، وأقصر طريق لتشغيل الدخول الحقيقي.
> **الحفظ الدائم يظل معطّلًا للاستخدام إلى أن يُختبر التكامل فعلًا.**

## ١. ما تحقّقنا منه من التوثيق الرسمي

المصدر: [Supabase — Creating a Supabase client for SSR](https://supabase.com/docs/guides/auth/server-side/nextjs)، آخر تحديث ٢٢ أكتوبر ٢٠٢٦. النسخ المثبتة في المشروع: **Next.js 16.4.5** و**React 19.3.1**.

| البند | ما قاله التوثيق الرسمي | أثره على هذا المشروع |
|---|---|---|
| الحزم المطلوبة | `@supabase/supabase-js` + `@supabase/ssr` | غير مثبتتين في المشروع حاليًا (`node_modules/@supabase` غير موجود). |
| أسماء المتغيرات | `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | الاسم الجديد «Publishable key»؛ قبلناه مع الاسم القديم `..._ANON_KEY` توافقًا. |
| ملف تحديث الجلسة | في **Next.js 16** اسمه `proxy.ts` والدالة `export async function proxy`. قبل ١٦ كان `middleware.ts` | لو استخدمنا `middleware.ts` هنا فلن تُستدعى أبدًا وتنتهي الجلسة بصمت. |
| التحقق من الهوية على الخادم | `supabase.auth.getClaims()` يتحقق من توقيع الرمز. **لا** تثق بـ `getSession()` في كود الخادم لأنه يقرأ الكوكي دون إعادة تحقق | كل مسار دائم وكل Server Action وكل RPC لازم يتحقق على الخادم، مش بس إخفاء الصفحة. |
| `getUser()` | استدعاء شبكي لسجل المستخدم المحدّث | يُستخدم عند الحاجة لبيانات المستخدم لا كبديل عن التحقق. |
| إصدارات متاحة (فحص سجل الحزم، قراءة فقط) | `@supabase/ssr@0.12.7`، `@supabase/supabase-js@2.119.0` | تُثبّت بنسخ محددة عند السماح، لا بتحديثات واسعة. |

## ٢. العائق الحالي (بصراحة، دون تجميل)

1. لا توجد حزم `@supabase/*` مثبتة في المشروع.
2. لا يوجد Docker ولا Supabase CLI ولا PostgreSQL خدمة على الجهاز؛ التحقق الحالي يعمل على PostgreSQL معزول داخل الذاكرة فقط (PGlite 0.5.15).
3. لذلك **لا يوجد GoTrue/Auth حقيقي** لاختبار: الدخول، استرجاع كلمة المرور، انتهاء الجلسة، الخروج، والوصول المباشر للمسارات.
4. محاكاة `auth.uid()` الموجودة في `supabase/tests/00_isolated_harness.sql` تختبر **الصلاحيات داخل القاعدة فقط**، وليست بديلًا عن اختبار تسجيل الدخول.

**النتيجة:** المرحلة D «مكتوبة ولم تُختبر». لا يُعرض أي زر حفظ دائم، ولا يُقال إن البيانات محفوظة فعليًا. مسارات `/demo/*` تبقى مستقلة بالذاكرة كما هي.

## ٣. الملفات المُعدّة بالفعل في هذه الحزمة

| الملف | الغرض | الحالة |
|---|---|---|
| `.env.example` | أسماء المتغيرات بقيم فارغة فقط، بلا أسرار | موجود |

## ٤. إعداد مطلوب لاحقًا (على السحاب، **لم يُنفّذ**)

> ⚠️ كل ما في هذا القسم **لم يُنفّذ** ولا يُنفّذ دون إذن صريح ومحدد من المستخدم.

1. إنشاء حساب المالك **إداريًا** من لوحة Supabase Auth (لا تسجيل عام، ولا زر Create account في الواجهة).
2. ضبط **Site URL** على عنوان التطبيق، وإضافة **Redirect URLs** المسموحة، وأهمها:
   - `http://localhost:3000/auth/callback` للتجربة المحلية.
   - عنوان النشر `/auth/callback` عند السماح بالنشر لاحقًا.
3. ضبط قالب بريد استرجاع كلمة المرور ليشير إلى `/auth/callback`، مع **رسالة عامة لا تكشف وجود الحساب من عدمه** عند طلب الاسترجاع.
4. بعد إنشاء المستخدم إداريًا، تُستدعى مرة واحدة فقط دالة `public.app_set_initial_owner(<uuid>)` **من جهة إدارية موثقة** (محرر SQL في لوحة Supabase أو CLI)، لا من المتصفح. الدالة مسحوب منها `EXECUTE` من `anon` و`authenticated`، ومحمية بقفل يمنع التهيئة المتزامنة، وتتحقق من وجود المستخدم في `auth.users`.
5. لا تُخزّن كلمة المرور في `business_settings` ولا في `localStorage`. لا يوضع `service_role` في المتصفح أو المستودع إطلاقًا.
6. حماية المسارات الدائمة وكل Server Action / Route Handler / RPC على **الخادم** بـ `getClaims()`، مع منع إعادة التوجيه إلى نطاق خارجي (`isAllowedRedirectPath`).

### أقصر خطوات عملية لفك العائق

1. تثبيت الحزمتين بنسخ محددة داخل مساحة العمل (`@supabase/ssr@0.12.7` و`@supabase/supabase-js@2.119.0`) بعد موافقة المستخدم على إضافة اعتمادية وقت التشغيل.
2. إنشاء `apps/web/src/lib/supabase/client.ts` و`server.ts` و`proxy.ts` وفق التوثيق الرسمي، وملف `proxy.ts` في جذر التطبيق.
3. تشغيل Supabase محلي (يحتاج Docker) أو ربط مشروع اختباري منفصل — **ليس مشروع الإنتاج ولا بيانات أولاد سليم الحقيقية**.
4. اختبار: غير المسجل، المالك، مستخدم آخر، جلسة منتهية، الخروج، الروابط المباشرة، ومسار استرجاع كلمة المرور. إن تعذّر البريد الحقيقي يُستخدم بريد Supabase المحلي ويُسجّل صراحة ما لم يُختبر خارجيًا.

## تحديث H039 — ٥ نوفمبر ٢٠٢٦ (تطبيق حراسة مؤقتة، لا Auth)

بدأنا `AUTH-01/PREP` بعد دمج H038. موجود على فرع `feat/auth01-safe-boundary-h039` ملف `apps/web/src/proxy.ts` في Next16، **يمنع** مسارات العمل الدائم ولا يسمح بتسجيل دخول أي شخص حتى يُربط `@supabase/ssr` و`supabase-js` وتُختبر هوية المالك الحقيقية. صفحة `/login` تنبيه فقط بدون كلمات مرور. الاختبار `tools/auth-boundary-smoke.mjs` يفحص HTTP عبر Next مع غياب الأسرار والسحابة. **إضافة الحراسة ليست دليلًا على جلسة سليمة ولا تُعد إتمام AUTH-01**.

المرجع الحالي: [Supabase creating a client](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&package-manager=npm) و[Next.js 16 Proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy). المرحلة التالية بعد اعتماد هذا الجزء هي حزم Supabase الرسمية و`client.ts`/`server.ts`/تحديث جلسة Proxy بـ`getClaims()`، مع تحقق المالك داخل الخادم وبيئة Auth منفصلة. لا تُفتح مسارات Server Action/HTTP أو تفوّض كتابة لعميل فقط لأنه يحمل cookie.

## H040 — استئناف التكامل الحقيقي بعد دمج الحراسة التمهيدية

حُسمت مرحلة الحماية **المؤقتة فقط**: PR #2 مدموج على `main` (`df6f54c7`)، CI `41944665834` نجح بما فيه HTTP smoke (١٢ GET محميًا/٦ POST مرفوضة، وdemo/login/assets سليمة). صفحة `/login` **ليست تسجيل دخول**، وProxy تمنع أي مسار غير عام حتى عند ضبط متغيرات الاتصال.

**التكامل المطلوب التالي:** `@supabase/ssr` + `@supabase/supabase-js` مع نسخ مقفلة وlockfile صحيح، ثم إنشاء عملاء Browser/Server، تحديث Proxy لإدارة الكوكي، والتحقق من الهوية عبر `getClaims()` والمالك بكل endpoint. لا اختبار Auth ناجح بدون GoTrue/PostgREST في مشروع اختبار منفصل؛ لا تُقبل محاكاة PGlite بدل اختبار الدخول. لا ترسل أسرار للمحادثة أو الريبو.

## H041 — تركيب SDK الرسمي فقط (٥ نوفمبر ٢٠٢٦)

على [PR #4](https://github.com/body199-cmyk/1-mohamed/pull/4) يوجد عميل Browser وعميل Server، ومساعد Proxy candidate لتحديث الكوكي، وفاحص مالك يبدأ بـ`getClaims()` ثم `app_is_owner()`. الإصدارات المثبتة: `@supabase/ssr@0.12.7` و`@supabase/supabase-js@2.119.0` مع npm lockfile بنسخة 3.
