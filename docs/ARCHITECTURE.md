# التصميم العام والمعمارية

الحالة: معتمدة كأساس معماري للتطبيق بعد APP-01؛ تم تحديثها في مهمة **DB-01-PREP** لتحديد بنية الحفظ الدائم والمصادقة وربط الحزم القائمة. توجد معاينة مؤقتة وحزم منطق مستقلة؛ التطبيق الإنتاجي وقاعدة البيانات الفعلية لم يُنفذا بعد (لا migrations أو نشر).

## ٢. هيكل المستودع الموحد واستخدام الحزم المستقلة دون إعادة كتابة

يعتمد المشروع بنية المستودع الموحد (`npm workspaces`) مع بقاء الحزم المستقلة وحدات نقية (Pure Domain Packages) لا تعتمد على React أو Next.js أو قاعدة البيانات:

```
┌────────────────────────────────────────────────────────────────────────┐
│                          apps/web (Next.js 16)                         │
│  - شاشات العرض والتفاعل والمكونات (React 19)                            │
│  - مسارات المعاينة بالذاكرة: /demo/*                                   │
│  - مسارات التطبيق الدائم المحمي: /trips, /contractors, /payments, ...  │
└───────┬───────────────────┬────────────────────┬───────────────────┬───┘
        │                   │                    │                   │
        ▼                   ▼                    ▼                   ▼
┌───────────────┐   ┌───────────────┐    ┌───────────────┐   ┌───────────────┐
│  @ledger/     │   │  @ledger/     │    │  @ledger/     │   │  @ledger/     │
│  accounting   │   │  trip-entry   │    │  contractor-  │   │  statement-   │
│               │   │               │    │  statements   │   │  export       │
│ • حساب المبالغ│   │ • آلة حالة    │    │ • بناء الكشف  │   │ • تصيير HTML  │
│ • تجميع النقلة│   │   تسجيل الشغل │    │ • الرصيد      │   │ • تصيير CSV   │
│ • تنسيق EGP   │   │ • ربط السعرين │    │   التراكمي    │   │ • CSS الطباعة │
└───────────────┘   └───────────────┘    └───────────────┘   └───────────────┘
```

### كيف تستخدم الواجهة وطبقة البيانات الحزم القائمة دون إعادة كتابتها؟
1. **حزمة الحسابات (`@ledger/accounting`):**
   - تستخدمها شاشات الإدخال لعرض معاينة فورية بالقرش (`calculateTripAmounts`).
   - تستخدمها طبقة إدخال البيانات (`src/data/trips/` [مخطط]) لتأكيد صحة المبالغ قبل أو أثناء إنشاء المعاملة.
2. **حزمة محرك الإدخال (`@ledger/trip-entry`):**
   - تستخدمها شاشات تسجيل النقلات لإدارة حالة المسودة (`createEntryState`, `reduceEntry`)، وتطبيق المشترك الاختياري، وربط وفك السعرين، دون تغيير أي كود فيها.
3. **حزمة كشف المقاول (`@ledger/contractor-statements`):**
   - تُمرر لها حركات الفترة المستخرجة من قاعدة البيانات كمدخلات نقية (`movements`) مع الرصيد السابق والافتتاحي (`opening`)؛ لتقوم الحزمة نفسها بفرز وترتيب الحركات وبناء الأرصدة التراكمية وتحديد المستفيد (`buildContractorStatement`).
   - يضمن هذا تطابق كشف الحساب الدائم بنسبة 100% مع اختبارات الحزمة وبيئة المعاينة.
4. **حزمة التصدير (`@ledger/statement-export`):**
   - تأخذ نفس كائن الكشف الناتج من حزمة الكشوف وتحوله إلى HTML جاهز للطباعة أو ملف CSV بترميز UTF-8 مع BOM؛ دون أي إعادة حساب.

## ٣. بنية الحفظ الدائم وعزل بيئة المعاينة (Persistence vs Demo Isolation)

للحفاظ على أمان العمل والتأكد من عدم اختلاط البيانات التجريبية بالحسابات الدائمة:

```
                                  مسار الطلب (Request Routing)
                                                │
                     ┌──────────────────────────┴──────────────────────────┐
                     ▼                                                     ▼
        مسارات المعاينة المؤقتة                                  مسارات التطبيق المحمي
           (/demo/trips, /demo/contractors)                       (/trips, /contractors, ...)
                     │                                                     │
                     ▼                                                     ▼
     ┌───────────────────────────────┐                     ┌───────────────────────────────┐
     │  ذاكرة الجلسة (Demo Context)   │                     │  وسيط الحماية (Middleware)     │
     │  - In-Memory React State      │                     │  - التحقق من جلسة Supabase    │
     │  - شريط تحذير صريح للبيانات   │                     │  - توجيه غير المسجل لـ /login │
     │  - تمسح عند تحديث الصفحة      │                     └───────────────┬───────────────┘
     └───────────────────────────────┘                                     │
                                                                           ▼
                                                           ┌───────────────────────────────┐
                                                           │  طبقة البيانات (Data Layer)   │
                                                           │  - Server Actions / Data SDK  │
                                                           │  - التحقق المالي ومعرف الطلب   │
                                                           └───────────────┬───────────────┘
                                                                           │
                                                                           ▼
                                                           ┌───────────────────────────────┐
                                                           │  قاعدة بيانات Supabase         │
                                                           │  - سياسات RLS للمستخدم الواحد  │
                                                           │  - معاملات ذرية وقفل تسلسلي   │
                                                           └───────────────────────────────┘
```

### ضوابط العزل بين البيئتين:
1. **عزل المسارات:**
   - تظل مسارات `/demo/*` قائمة ومستقلة، تعمل بذاكرة الجلسة التفاعلية (`DemoStoreProvider`) وبشريط التنبيه الأصفر الصريح؛ لتظل بيئة معاينة آمنة لتجربة الواجهة دون المساس بقاعدة البيانات.
   - المسارات الدائمة (`/trips`, `/contractors`, `/payments`, `/reports`, `/settings`) لا تستخدم `DemoStoreContext` إطلاقًا، بل تتصل بطبقة البيانات الدائمة.
2. **حراسة المسارات عبر Next.js Middleware:**
   - يفحص وسيط الحماية مسارات التطبيق الدائمة؛ إذا لم تكن هناك جلسة مصادقة نشطة من Supabase Auth، يُعاد توجيه المتصفح تلقائيًا إلى صفحة تسجيل الدخول `/login`. مسارات `/demo/*` تظل عامة للمعاينة.

## ٤. تدفق البيانات، تأكيد الحفظ، ومنع ادعاء النجاح الوهمي

تتبع العمليات المالية دورة تدفق صارمة لا تدّعي النجاح مطلقًا قبل الحصول على تأكيد قطعي من الخادم:

```
[إدخال المستخدم] 
      │
      ▼
[تحقق محلي مبكر بالواجهة] 
      │ (أخطاء دقة، حقول ناقصة، أسعار غير متطابقة)
      ▼
[توليد/تثبيت معرف المحاولة المنطقية: idempotency_key]
      │
      ▼
[إرسال الطلب للخادم مع قفل زر الحفظ وإظهار حالة التحميل]
      │
      ├───────────────────────┬────────────────────────┐
      ▼                       ▼                        ▼
[فشل اتصال / Timeout]   [رفض مالي / تعارض إصدار]   [تأكيد الحفظ بالخادم 200/201]
      │                       │                        │
      ▼                       ▼                        ▼
[إبقاء المسودة كاملة]   [عرض رسالة واضحة للمستخدم]  [تحديث البيانات المتأثرة]
[إتاحة إعادة الإرسال]   [إبقاء المسودة للتصحيح]   [إفراغ المسودة ببدء نقلة جديدة]
[بنفس معرف الطلب W01]   [دون خصم أو مساس بالحساب] [إشعار نجاح مؤكد للمستخدم]
```

### القواعد الصارمة لتأكيد الحفظ:
1. **لا تفاؤل زائف (No Unconfirmed Optimistic Success):** لا يُغلق نموذج الإدخال ولا تُفرغ المسودة ولا يُدرج السجل في القوائم الدائمة بمجرد الضغط على الزر، بل يُقفل الزر فورًا بمؤشر تحميل مرئي (`Submitting...`) حتى يرد الخادم بنتيجة المعاملة.
2. **الحفاظ على المسودة عند الفشل:** إذا فشل الحفظ بسبب عجز رصيد أو انقطاع شبكة أو تعارض إصدار، تظل كافة مدخلات المستخدم في المسودة كما هي دون فقدان، وتُعرض رسالة خطأ صريحة تشرح سبب المشكلة لإتاحة التصحيح أو إعادة المحاولة.
3. **إعادة المحاولة بنفس المعرف (W01):** عند إعادة المحاولة بعد انقطاع الاتصال أو انتهاء المهلة، يُرسل المتصفح **نفس المعرف المنطقي (`idempotency_key`)** ونفس البيانات؛ فيقوم الخادم بإرجاع النتيجة المسجلة إن كانت العملية قد تمت بنجاح قبل انقطاع الشبكة، دون تكرار أي قيد مالي.

## ٥. طبقة البيانات والمصادقة المخططة (Data & Auth Architecture)

**جميع المسارات أدناه مخططة للتنفيذ اللاحق (موسومة بـ «مخطط»)؛ لا توجد كملفات منفذة الآن.**

```
apps/web/src/
├── lib/
│   └── supabase/                      # مكتبات ربط Supabase (مخطط)
│       ├── client.ts                  # عميل المتصفح للمصادقة واستعلامات العميل
│       ├── server.ts                  # عميل الخادم لـ Server Actions باستخدام الكوكيز
│       └── middleware.ts              # فحص وحراسة الجلسة في وسيط Next.js
├── data/                              # طبقة الوصول للبيانات والعمليات (مخطط)
│   ├── auth/                          # دوال الدخول والخروج واسترجاع كلمة السر
│   │   ├── auth-actions.ts
│   │   └── auth-session.ts
│   ├── contractors/                   # استعلامات وإضافة المقاولين
│   │   └── contractors-data.ts
│   ├── vehicles/                      # استعلامات وإضافة وتعديل العربيات
│   │   └── vehicles-data.ts
│   ├── trips/                         # عمليات حفظ وتعديل وإلغاء النقلات
│   │   ├── trips-actions.ts           # استدعاء المعاملات الذرية بمعرف الطلب
│   │   └── trips-queries.ts           # قراءة نقلات اليوم أو فترات العمل
│   ├── payments/                      # عمليات تسجيل وتعديل وإلغاء الدفعات
│   │   ├── payments-actions.ts        # سداد الدفعات مع فحص D13-B وقفل الحساب
│   │   └── payments-queries.ts        # استعلام دفعات حساب العربية
│   └── reports/                       # استخراج كشوف الحسابات بلقطة قراءة متسقة
│       ├── contractor-reports.ts      # تجميع حركات المقاول وتمريرها لحزمة الكشف
│       └── vehicle-reports.ts         # تجميع كشف حساب العربية لدى المقاول
```

### حدود حجم الملفات ومسؤولياتها:
- تلتزم كافة ملفات الكود المصدري اليدوية بحد **٢٠٠–٣٠٠ سطر**، ولا تتجاوز ٤٠٠ سطر إلا لضرورة مبررة تسجل بالوثائق.
- يُحظر إنشاء ملف مركزي ضخم (مثل `store.ts` أو `god-service.ts`) يجمع الواجهة والبيانات والمصادقة؛ بل تُقسم المسؤوليات إلى وحدات مستقلة وصغيرة كما هو موضح بالهيكل أعلاه.

## ٦. الأمان وعزل الأسرار (Security & Secrets Isolation)

1. **Supabase Auth للمستخدم المالك الواحد:**
   - الحساب يُنشأ يدويًا من لوحة التحكم، والتسجيل العام معطل تمامًا.
   - الجلسة تُدار عبر توكن JWT في كوكيز آمنة (`HttpOnly, Secure, SameSite=Lax`).
   - تسجيل الدخول وحده لا يمنح ملكية البيانات؛ يجب مطابقة `auth.uid()` مع هوية المالك المعتمدة في `public.app_owner`.
2. **سياسات الأمان على مستوى الصف (RLS) ومنع الكتابة المباشرة:**
   - تُفعل سياسة RLS الصارمة على جميع جداول PostgreSQL وتفرض التحقق من المالك حصريًا عبر `public.app_is_owner()`، وتمنع وصول المفتاح المجهول `anon` أو أي مستخدم مسجل غير المالك.
   - الكتابة المباشرة من العميل (`INSERT, UPDATE, DELETE`) محظورة كليًا عبر RLS (`WITH CHECK (false)`)؛ كافة التعديلات المالية والإدارية تمر حصريًا عبر دوال RPC محمية ذات صلاحيات مقيدة وضبط مسار آمن (`SET search_path = pg_catalog, public, auth` — مصحح في BUILD-01/A لمطابقة الملفات الفعلية).
  - **تصحيح BUILD-01/A:** `TRUNCATE` لا يخضع لـ RLS إطلاقًا؛ تُسحب صلاحيته صراحةً من `anon`/`authenticated` على الجداول المحمية والجداول المستقبلية. كذلك حماية هوية المقاول الأساسي وسجل التدقيق بمُحفّزات على مستوى الجدول لا بالواجهة فقط.
3. **عزل المفاتيح والأسرار:**
   - المفاتيح العامة المتاحة للمتصفح تقتصر على `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY`.
   - المفتاح الإداري `SUPABASE_SERVICE_ROLE_KEY` **محظور كليًا في المتصفح أو المستودع**، ولا يستخدم لتجاوز حماية عمليات المستخدم اليومية.

## ٧. اتساق التقارير وتعدد الصفحات (Pagination Consistency)

- لا يكفي استخدام `REPEATABLE READ` في استعلام صفحة واحدة لضمان اتساق تقرير يُقرأ عبر طلبات HTTP منفصلة؛ لأن كل طلب يمثل معاملة مستقلة.
- آلية القراءة المتسقة للكشوف وتصديرها ستعتمد على مؤشر زمني أو لقطة قراءة موحدة (Snapshot Cursor Token) في الخادم تُثبت وتُختبر في مهمة الكشوف `DB-05-STATEMENTS`.
