# استرجاع بيانات مشروع محمد — دليل التشغيل والقبول (20 نوفمبر 2026)

## هدف التطوير

وجود Excel ونسخ يومية على Google Drive مفيد للقراءة، لكنه لا يعيد قاعدة البيانات تلقائيًا. هذا التطوير يفصل ثلاثة سيناريوهات، ولا يسمح بدمج بيانات مالية عشوائيًا.

### أ — نقلة أو دفعة اتلغت بالغلط (أصبح قابلًا للاستعادة من الإعدادات)

1. صاحب المشروع يسجل الدخول إلى الموقع.
2. الإعدادات → النسخ الاحتياطي واستعادة البيانات → «استعادة نقلة أو دفعة ملغاة».
3. اختَر نوع السجل، ثم «عرض السجلات الملغاة».
4. اختَر **الرقم الأصلي**، وراجع تاريخ الحركة والحساب والقيمة والسبب السابق.
5. اكتب سبب الاستعادة، ووافق على تأثيرها المالي، واكتب «استعادة» للتأكيد.
6. يعيد النظام تفعيل السجل الأصلي فقط، مع إضافة تدقيق وإصدار جديد. لن ينشئ ID جديدًا، ولن يعيد دفعات أو نقلات أخرى تلقائيًا.
7. **استعادة دفعة** قد تُرفض إذا كانت ستخلق رصيدًا نقديًا سالبًا في أي يوم تاريخي (D16). **استعادة نقلة** تعيد عملها إلى الحساب الأصلي، ويمنع FIN-04 التواريخ التي تخالف افتتاح النقدية.

الحماية: `app_require_owner()` (ليس أي موظف)، `expected_version`، مفاتيح idempotency، قفل حساب العربية، حركات داخل معاملة واحدة و`audit_log`. لا توجد صلاحية SQL مباشرة لأعضاء المشروع.

### ب — قاعدة البيانات ضاعت أو باظت: بيانات الأعمال من Google Drive

**مرحلة إنقاذ حقيقية لكنها عملية إدارية محمية، وليست زرًا يعيد الكتابة فوق المشروع الحالي.**

المدخلات: نسخة `1-mohamed-YYYY-MM-DD-restore.tar.gz` داخل مجلد Google Drive المعتاد، و**مشروع Supabase آخر وفارغ** طُبقت عليه نفس migrations، وحساب PostgreSQL منفصل خاص بذلك المشروع. يجب عدم إعادة استعمال قاعدة الإنتاج نفسها مطلقًا.

1. إنشاء مشروع Supabase جديد منفصل وتطبيق migrations من نفس `main`، بدون إدخال أي بيانات أعمال.
2. حفظ رابط اتصال PostgreSQL الخاص به `RESTORE_DB_URL` في GitHub Secrets داخل البيئة المحمية `google-drive-backup`. **لا ترسل الرابط أو كلمة المرور في الدردشة أو في مدخلات Actions أو في سجل عام**.
3. فتح GitHub → Actions → `Emergency recovery to a separate empty Supabase project` → `Run workflow`.
4. إدخال تاريخ النسخة، وREF المشروع البديل (20 حرفًا)، والتأكيد الحرفي `RESTORE_TO_EMPTY_SEPARATE_PROJECT`.
5. لو قاعدة المصدر متاحة: سيقرأ النظام `backup_history` من المصدر بصفقة READ ONLY، ويطابق تاريخ النسخة وID ملف Drive والبصمة والحجم، ثم يفكها ويستعيدها في قاعدة PGlite مؤقتة للتدقيق، وبعدها يستعيد **تسعة جداول أعمال فقط** إلى المشروع البديل الفارغ داخل معاملة واحدة؛ إن فشلت أي خطوة لا تحدث كتابة جزئية.
6. لو قاعدة المصدر غير متاحة: اختيار `source_database_unavailable`. يبحث Drive باسم ملف مضبوط وتاريخ محدد ولا يتصل بالمصدر. يفضل إدخال SHA-256 الموثوقة سابقًا من السجل، وإذا تعذرت يجب التصريح `I_ACCEPT_UNVERIFIED_SOURCE_TO_EMPTY_TARGET_ONLY`؛ عند غياب بصمة خارجية يُثبت فقط الاتساق الداخلي للملف/الـmanifest، وليس أصالة المصدر. **لا يُسمح في هذه الحالة إلا بمشروع بديل فارغ.**
7. لا يتم تغيير Vercel أو حسابات الدخول تلقائيًا. يجب إنشاء/ربط Auth للمشروع البديل، وضبط owner/member IDs، واختبار دخول المالك والمستخدمين ومطابقة أرصدة المقاولين والعربيات والتقارير قبل أي cutover يدوي.
8. احتفظ بالمشروع الأصلي إن كان متاحًا كنقطة رجوع؛ لا تحذف منه شيئًا.

**حدود ملف الاسترجاع التسعة:** `contractors, vehicles, vehicle_accounts, business_settings, opening_balances, trips, payments, audit_log, idempotency_keys`. لا يتضمن `auth.users` أو `auth.identities` أو `app_owner` أو `app_members` أو سجل `backup_history`. ملف Excel هو للقراءة فقط وليس مصدر استرجاع محاسبي موثوق.

لا تتوقع تشغيل الـworkflow بنجاح حتى تكون صلاحيات وsecret `RESTORE_DB_URL` والقاعدة البديلة مهيأة. دون ذلك سيرفض النظام الاسترجاع بدل المخاطرة.

### ج — سجل محذوف حذفًا نهائيًا أو دمج جزء من نسخة قديمة مع الجديدة

هذا **ليس** مثل الإلغاء العادي. لا تعيد تشغيل نسخة قديمة فوق قاعدة الإنتاج؛ ستفقد البيانات الأحدث. يجب:

1. استعادة نسخة Drive إلى قاعدة أخرى.
2. مقارنة ID السجل وتوابعه المحاسبية والنسخة الحالية.
3. إرجاع السجل فقط بعملية محاسبية متخصصة مع تأكيد الهوية وصحة المبالغ والتواريخ ومفاتيح idempotency.
4. المقارنة والاختبارات وتوقيع مراجعة إن كان التاريخ المالي متعارضًا.

لا يوجد حاليًا استيراد آلي لسجل محذوف فعليًا من الأرشيف إلى الإنتاج؛ هذا المسار يجب ألا يدعي اكتماله. الحذف الفعلي محظور في واجهة المشروع الحالية، والإلغاء يحتفظ بالسجل.

## بوابة الاختبارات قبل أي دمج

- `npm run db:verify` يشغّل Migration الاستعادة واختبار `22_cancelled_record_recovery_verification.sql` في قاعدة PGlite معزولة، بما فيه تدقيق الصلاحيات والإعادة ومنع تكرار الدفعات وD16 والرجوع التلقائي عند الفشل.
- `npm run test:web` واختبارات Chromium لهوية المالك وتأكيدي الاستعادة وثبات مفتاح الطلب بعد الخطأ.
- الاختبارات الأصلية للحسابات والنسخ وPDF والصور والموبايل.
- اختبار صلاحيات ووظائف RPC على Supabase لا يفترض أن CI يغطي Auth الحقيقي. عند تسليم ميزة الاستعادة يلزم تجربة قبول مالك على بيانات تجريبية فقط، لا تحريك حركات مالية إنتاجية لأغراض الاختبار.
- يجب ألا تُطبّق migration الإنتاج إلا بعد نجاح CI؛ عندها نشر الكود بعد التحقق. يجب عدم تنفيذ استرجاع فعلي على بيانات الإنتاج أثناء الاختبار.
