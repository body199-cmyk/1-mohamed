# خطة الاستكمال بدون ربط الحسابات أولًا — H042

**تاريخ قرار الترتيب: ٥ نوفمبر ٢٠٢٦.**
**طلب المستخدم:** نكمل ما يمكن من التطبيق نفسه، ونؤجل ربط حسابات Supabase وVercel لأواخر المشروع. هذا **تعديل لترتيب التنفيذ لا إلغاء لضرورة اختبار الحفظ والمصادقة الحقيقيين**. لا بيانات إنتاج، ولا أسرار، ولا ادعاء بأن تطبيقًا تجريبيًا معزولًا يعادل نظامًا ماليًا جاهزًا.

## الواقع المؤكد عند الاستلام

- `DB-03/H038` [PR #1](https://github.com/body199-cmyk/1-mohamed/pull/1) مدموج: جدول النقلات وعمليات SQL ووصف الطريق والإيصال والملاحظات واختبارات منع التكرار/التدقيق (PostgreSQL معزول فقط).
- `AUTH-01/PREP/H039` [PR #2](https://github.com/body199-cmyk/1-mohamed/pull/2) مدموج: حارس **منع افتراضي** للمسارات غير العامة، وصفحة `/login` لا تقبل بيانات دخول.
- `H040` [PR #3](https://github.com/body199-cmyk/1-mohamed/pull/3) مدموج: الحالة ونقطة الاستئناف.
- `AUTH-01/SDK/H041` [PR #4](https://github.com/body199-cmyk/1-mohamed/pull/4) مدموج: حزمتا Supabase بنسخ ثابتة وعميل Browser/Server ومساعد صاحب الحساب والجلسات، **غير مُفعّلة**، بعد مراجعة نقدية وCI نجاح؛ لا مشروع Supabase حي.
- المعاينة `/demo/trips` و`/demo/contractors`، محرك الحساب، الإدخال، كشف المقاول، HTML وCSV موجودون؛ لا دفعات، لا حفظ دائم من الواجهة، لا تصدير صورة أو XLSX فعلي، لا استعادة نسخ فعلية.

## الترتيب الجديد والأولويات

| الترتيب | العمل القابل للتنفيذ دون توصيل الحسابات | حالة البدء/حدود قبول الاختبارات |
|---|---|---|
| **1. UI-BASE** | استكمال شاشات بيانات المقاولين والعربيات وحسابات العربيات والأرصدة الافتتاحية ببيانات **تجريبية معزولة**، والإضافة والبحث والتعديل والأرشفة والتحقق | يمكن الآن؛ قبولها فقط بعد اختبارات UI/E2E وحالات إدخال خاطئة، **لا يُدعى حفظ دائم** |
| **2. PAYMENTS** | جدول الدفعات، عمليات CREATE/UPDATE/CANCEL المحمية، حساب الرصيد وتدقيق وتعارض التعديل ومنع دفع زائد، وشاشة إدخال الدفعات بالبيانات التجريبية | **يتطلب حسم D15 وD16 قبل إقرار الحساب الزمني**؛ يمكن تجهيز fixtures واختبارات مستقلة دون افتراض القرار |
| **3. REPORTS** | الرئيسية، يومية الشغل، كشف حساب كل عربية لدى المقاول المسؤول، الفلاتر وفتراتها، توحيد سابق/حركات/ختامي مع محرك الحساب | محرك كشف المقاول موجود؛ يجب ألا يخلط فرق الشغل بالنقد أو يحسب الدفعة في تاريخ النقلة |
| **4. EXPORT** | إخراج صورة واضحة + PDF مرتب مرقم + Excel عند تثبيت النطاق، بالاعتماد على **نفس نتيجة الكشف** وليس إعادة الحساب | الموجود حاليًا HTML للطباعة وCSV فقط؛ القبول بمقارنة شاشة/ملف على fixtures واقعية |
| **5. BACKUP-CORE** | صيغة نسخ مرقمة، تحقق شامل من سلامة الملف واكتماله، استعادة ذرية تجريبية وتراجع عند الفشل، تقارير تحقق/خطة رجوع | يمكن اختبار محرك استرجاع معزول؛ **نسخ Supabase المجدولة والحفظ الآمن الحقيقي يؤجلان للتكامل**؛ تفاصيل D07 تحتاج حسم قبل الاحتفاظ |
| **6. QUALITY** | فحص UX RTL/Cairo والداكن والفاتح والجوال والتابلت، تيسير الوصول، اختبارات E2E، المراجعة النقدية الأمنية/المحاسبية والأداء | ممكن على المعاينة وfixtures؛ **مراجعة إصدار الإنتاج لاحقًا بعد الربط** |
| **7. SUPABASE-TEST** | ربط مصادقة مالك حقيقية، GoTrue/PostgREST، تشغيل migrations على **مشروع اختباري**، API/RLS/HTTP والجلسات، ربط الواجهات بالحفظ الدائم واسترجاع النسخ، تجارب التزامن | **هنا فقط نحتاج وصولًا آمنًا إلى Supabase اختباري**؛ لا يُستخدم حساب إنتاج قبل نسخة أمان وخطة رجوع |
| **8. VERCEL-RELEASE** | ربط مستودع GitHub بالنشر التجريبي، متغيرات آمنة، تجربة نهاية-لنهاية على Vercel، قبول المستخدم وخطة إصدار/تراجع | يحتاج اتصال Vercel **في آخر مرحلة**؛ لا نشر عام بأموال حقيقية دون قبول الاختبارات |

**ليست قائمة متتابعة بلا استثناء:** كل مهمة مستقلة تُنفذ على فرع وPR منفصل مع اختبار مناسب ومراجعة نقدية ثانية والتوثيق والدمج. لا تعني `UI-BASE` أو `PAYMENTS` على fixtures أن العمليات حُفظت في Supabase. عند اكتشاف اعتماد يمنع مهمة، انتقل إلى مهمة مستقلة مع توثيق سبب التأجيل.

## القرارات التي لا نخترع إجاباتها

- `D15`: ترتيب استحقاق الشغل والدفعة **في اليوم نفسه** عندما لا توجد ساعة مسجلة. له تأثير على حساب رصيد الدفعات التاريخي؛ يُحسم من المستخدم قبل كتابة منطق `PAYMENTS`.
- `D16`: هل يجب فحص كل الرصيد في **كل تاريخ وسيط** عند إدخال دفعة متأخرة، أم الاكتفاء بفحص الرصيد في تاريخ الدفعة واليوم وفق `D13-B`؟ يجب قرار المستخدم قبل التنفيذ المالي.
- `D07`: مكان النسخ وسياسة الاحتفاظ والاستعادة، يُحسم قبل نسخ الأمان الواقعي؛ يمكن إعداد اختبارات وأداة تحقق أولًا.
- لا تغير A01 (فصل الشغل عن النقد) وA12/D13-B وD01/D14؛ هذه معتمدة وتظل المصدر الوحيد للمنطق.

## بوابات النجاح لكل بطاقة

1. افحص `AGENTS.md` و`STATUS.md` و`TASKS/SUBTASKS` والكود الفعلي؛ اكتب Scope/Acceptance على الفرع.
2. نفّذ في طبقة محددة، ولا تضف تكاملًا سحابيًا أو تعدل migrations سابقة بصمت.
3. أعد قراءة كامل `diff` بمرور **نقدي منفصل**، وأضف اختبارات للثغرات المكتشفة.
4. شغّل CI على آخر commit؛ سجّل الـrun وصلاحيته وحدود الاختبار، لا تقول PASS قبل تشغيله.
5. حدّث `STATUS` + `TASKS/SUBTASKS` + `CODE_MAP` + `ISSUES` عند وجود خلل + `HANDOFF_LOG`. ثم ادمج PR بعد المراجعة ونجاح الاختبارات وتحقق من `main`.

**أول بطاقة مقترحة بعد H042:** `UI-BASE-01`، شاشة إدارة المقاولين والعربيات والأرصدة بالذاكرة التجريبية، من غير اتصال بـSupabase؛ يُراجع محتوى `apps/web/src/demo` والحزم أولًا لتجنب تكرار الوظائف القائمة.

## متى نحتاج الحسابات فعلًا؟

- **حاليًا:** GitHub المتصل كافٍ لرفع كود واختبارات ومراجعة/دمج؛ لا تحتاج مشاركة أي كلمات مرور.
- **عند SUPABASE-TEST:** تفويض اتصال مناسب بمشروع **اختبار فقط** أو إعداد آمن يقوم به المستخدم، دون إرسال API secrets أو `service_role` للمحادثة/الريبو؛ نختبر مالك وغير مالك وجلسات منتهية وعمليات RPC حقيقية.
- **عند VERCEL-RELEASE:** اتصال Vercel وربط مستودع GitHub ومتغيرات سرية داخل المنصة وتجربة نشر على بيئة تجريبية، ثم قبول صريح قبل إنتاج.
