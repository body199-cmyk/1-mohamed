## FIN-A-001 — إعادة تعيين مسؤول النقلة بعد وجود دفعة

### المتوقع

إذا كانت الدفعة تحمل `linked_trip_id`، فيجب أن تظل النقلة والدفعة متوافقتين في الأقل على `vehicle_id` و`responsible_contractor_id`، أو يجب رفض تعديل النقلة، أو إعادة ربط/تسوية الدفعة ذريًا مع سجل تدقيق واضح. لا ينبغي أن تصبح النقلة جزءًا من كشف حساب حساب جديد بينما تظل الدفعة خصمًا من الحساب القديم.

### ما حدث فعليًا

أنشأت نقلة صناعية `FIN-T1` على `FIN_V1`، مسؤولها الأول `FIN_OWNER`، بقيمة عمل `10000` قرش. أنشأت بعدها دفعة `FIN-P1` بقيمة `5000` قرش، مرتبطة بـ`FIN-T1` وعلى مسؤول `FIN_OWNER`. بعد ذلك استدعيت:

```text
app_op_trip_update(
  'FIN-TRIP-MOVE',
  {
    id: 'FIN-T1',
    expected_version: 1,
    reason: 'move responsible contractor after payment',
    vehicle_id: 'FIN_V1',
    counterparty_contractor_id: 'FIN_C2',
    direction: 'OTHER_SUPPLIES',
    trip_date: '2026-11-02',
    weight_tonnes: '1',
    contractor_rate_egp: '100',
    vehicle_rate_egp: '100',
    expense_egp: '0'
  }
)
```

الاستدعاء نجح وأعاد `version=2` و`responsible_contractor_id=FIN_C2`. الصفوف بعده كانت:

```text
trip FIN-T1: responsible_contractor_id=FIN_C2, counterparty_contractor_id=FIN_C2
payment FIN-P1: responsible_contractor_id=FIN_OWNER, linked_trip_id=FIN-T1
```

أي أن العلاقة المرتبطة بقيت موجودة، لكن طرفيها الماليين لم يعودا متوافقين.

### أثر الكشوف

قبل التعديل:

- كشف نقدية `FIN_V1|FIN_OWNER`: النقلة `+10000` ثم الدفعة `-5000`، والإغلاق `15000`.
- كشف المقاول `FIN_C1`: النقلة `+10000`.

بعد التعديل:

- كشف `FIN_V1|FIN_OWNER`: لم يعد يرى النقلة، لكنه ظل يرى الدفعة `-5000`؛ `work_piastres=0` و`paid_piastres=5000` و`period_closing_piastres=5000`.
- كشف `FIN_V1|FIN_C2`: صار يرى النقلة `+10000` دون الدفعة.
- كشف المقاول `FIN_C1`: صار فارغًا.
- كشف المقاول `FIN_C2`: صار يرى النقلة `-10000`.

هذا ليس مجرد تغيير عرض؛ إنه نقل للنشاط إلى حسابين منفصلين مع بقاء معرف الدفعة يشير إلى النقلة نفسها.

### مواضع الكود ذات الصلة عند SHA `6e0146d`

- `supabase/migrations/20261104200023_phase_c_trip_details.sql:183-244` — `app_op_trip_update` يقفل الحسابين ويحدث `responsible_contractor_id`، لكنه لا يتحقق من وجود دفعات فعالة مرتبطة بالنقلة ولا يمنع تغيير الحساب.
- `supabase/migrations/20261104200031_payment_operations.sql:227-246` — تحديث الدفعة يتحقق من حسابات الدفعة، لكنه لا يفرض معالجة عكسية عند تعديل النقلة.
- `supabase/migrations/20261104200030_payments_schema.sql` — حارس علاقة الدفعة يُطبق عند كتابة الدفعة؛ الاختبار أثبت أن تعديل النقلة نفسها يتجاوزه.

### أمر الاختبار وحدود الدليل

```bash

```

الاختبار حمّل الـharness وmigrations من commit `6e0146d`، وأنشأ contractors/vehicle/accounts/openings صناعية، ثم نفذ create payment، read statements، trip update، trip cancel، وreplay. لم يستخدم إنتاجًا أو بيانات حقيقية. الدليل قوي على سلوك SQL في PGlite؛ لم يختبر واجهة UI أو PostgREST الحقيقي لهذا السيناريو.

## FIN-A-002 — إلغاء نقلة لها دفعة مرتبطة

### النتيجة

بعد نجاح:

```text
app_op_trip_cancel('FIN-TRIP-CANCEL', {
  id: 'FIN-T1', expected_version: 2,
  reason: 'cancel synthetic moved trip'
})
```

أصبحت النقلة `is_cancelled=true`, `version=3`، لكن الدفعة بقيت:

```text
payment_id=FIN-P1
payment_cancelled=false
responsible_contractor_id=FIN_OWNER
linked_trip_id=FIN-T1
```

أصنّفها **تحتاج قرارًا/اختبارًا** لا كعيب مؤكد، لأن تصميم المشروع قد يعتبر الدفعة حركة نقدية مستقلة لا تُلغى تلقائيًا. المطلوب من المنفذ تحديد القاعدة: هل إلغاء النقلة يجب أن يرفض وجود دفعة مرتبطة، أم يلغي/يعكس الدفعة، أم يبقيها مع تحذير وتسوية؟ ثم إضافة اختبار قبول للقرار.

## BACKUP-B-001 — سعة JSON وCSV محليًا

### الأمر

```bash
node --experimental-strip-types /tmp/audit100-backup-capacity.mjs
```

أنشأت الاختبار صفوف `trips` صناعية تحتوي نصًا عربيًا، وتركت الجداول الـ11 الأخرى فارغة، ثم قاس الزمن والحجم والتحقق من SHA-256.

### النتائج

| الصيغة | الصفوف | النتيجة | الحجم بالبايت | الزمن التقريبي | SHA/التحقق |
|---|---:|---|---:|---:|---|
| JSON | 49,999 | مقبول | 4,278,639 | 234.43 ms | SHA مطابق |
| CSV | 49,999 | مقبول | 4,428,035 | 324.26 ms | SHA محسوب، BOM وCRLF صحيحان |
| JSON | 50,000 | مقبول | 4,278,725 | 166.23 ms | SHA مطابق |
| CSV | 50,000 | مقبول | 4,428,124 | 264.29 ms | SHA محسوب، BOM وCRLF صحيحان |
| JSON | 50,001 | مرفوض | — | 0.23 ms | `PORTABLE_BACKUP_INVALID: Portable export exceeded 50,000 rows.` |
| CSV | 50,001 | **مقبول مباشرة** | 4,428,213 | 305.10 ms | BOM وCRLF صحيحان |

SHA-256 لنسخة JSON عند 50,000 صف:

```text
856571b99f7f4b9e3b57c1564fa6ea16d48abc25fd940e96bc792c457792c231
```

### تفسير الحد

- `apps/web/src/lib/backup/export.ts:22-41` يفرض `MAX_ROWS=50000` داخل `createPortableBackup`، لذلك JSON يرفض 50,001.
- `apps/web/src/lib/backup/export.ts:48-53` لا يفرض الحد نفسه داخل `serializeTableCsv`، لذلك CSV المباشر يقبل 50,001.
- `apps/web/src/app/api/backup/export/route.ts:56-67` يستدعي RPC snapshot قبل serializer.
- `supabase/migrations/20261119110000_portable_backup_snapshot.sql:18-46` يفرض حدًا إجماليًا قدره 50,000 ويرجع `P2011` قبل النقل.
- `supabase/tests/20_portable_backup_snapshot_verification.sql:33-40` يختبر حد SQL عند 50,001 صف، لكنه لا يختبر `serializeTableCsv` مباشرة عند 50,001.

لذلك لا أقدّم `BACKUP-B-001` كاختراق مؤكد لمسار HTTP الحالي؛ أقدمه كتفاوت عقدي يحتاج تحصينًا واختبارًا، خصوصًا إذا استُخدمت دالة CSV مستقبلًا خارج هذا RPC أو تغيّر مصدر البيانات.

## BACKUP-B-002 — drift ولقطة متسقة

### ما تم التحقق منه

- `npm run db:verify` مرّ كاملًا، بما في ذلك migration واختبارات portable backup.
- اختبار route المحلي مرّ، بما فيه تحويل خطأ RPC `P2010` إلى HTTP 409 بلا تنزيل.
- JSON عند 49,999 و50,000 صف استعاد بنيويًا عبر `JSON.parse`، وعدد الصفوف مطابق، وSHA المحسوب من archive مطابق للـSHA المضمّن.

### ما لم يُختبر

لا توجد في هذه البيئة قاعدة Supabase/Vercel معزولة أو اتصالات PostgreSQL مستقلة لإدخال تعديل بين القراءتين داخل `app_portable_backup_snapshot`. كما أن `tools/db-verify.mjs` يذكر صراحة أن PGlite اتصال واحد في الذاكرة ولا يمثل الطلبات المتزامنة الحقيقية.

الاختبار الموجود في `apps/web/e2e/backup-export-route.test.ts:54-60` يحقن `P2010` كـmock، لذلك يثبت ترجمة الخطأ في route ولا يثبت أن drift الحقيقي سيُكتشف. هذه نقطة **تحتاج اختبارًا في بيئة حقيقية**، وليست finding مؤكدة من هذا التدقيق.
