## ٣) المراجعة الفعلية للفروق (عيني، وليست منقولة)

### الحسابات والدفعات — `cash-ledger.ts`
- **D15/D16 (A04 §PLAN-02):** إعادة صياغة مرشّحات الحد الأدنى اليومي مطابقة للمعتمد: شغل اليوم نفسه يُضاف قبل تقييم الدفعة (D15)، وأرصدة دفعات اليوم نفسه تُحسب بعده (ترتيب `created_at`)، ولا تُعاد أرصدة شغل اليوم الوسيط للحد الأدنى. الرفض عند `min < amount` والقبول عند التساوي يطابق A12 (≤ المتبقي). المرشح الأول + قائمة الأرصدة اللاحقة + رصيد نهاية الفترة = تنفيذ D13-B + D16 صحيح. تم تتبع المثال الوسيط يدويًا (T1/T2/P1 في الاختبارات) والنتيجة مطابقة للقاعدة.
- **تعديل الدفعة (D13-B):** `applyDemoPaymentEdit` تحول ذري بلا تحريك حالة عند الرفض، واستبعاد النسخة القديمة عبر `excludingPaymentId` محفوظ، وإصدار+سبب+سجل قبل/بعد كما هو.
- **حماية فشل مقفول:** افتتاحي غير صالح = إيقاف الكشف كله؛ اتجاه نقلة تالف داخل الفترة = إيقاف كلا حسابي العربية على نفس العربية (مثبت باختبار)؛ نقلات مستقبلية فاسدة معزولة عن التقارير التاريخية ولا تمنع دفعة تاريخية صحيحة — يطابق مبدأ «الإسقاطات التاريخية معزولة» الموثق في الكود والاختبار.
- **FIN-07:** إزالة سقف التجميع على إجمالي النقد مع بقاء حدود كل حركة/دفعة/افتتاحي bigint موقّع؛ الحساب bigint دقيق بلا float، والـSQL يتجمع في `numeric` (مثبت باختبار SQL جديد). **هذا تغيير في مجال القيم المسموح به للرصيد التراكمي** — سجل المهمة الأصلي (FIN-07) وصفه «pending critical review»؛ يُرفع للمنسق للاعتماد الصريح كجزء من الحزمة.
- **حافة SQL السالبة القصوى:** `validOpeningPiastres` و`parseOpeningEgp` يقبلان الآن `-9223372036854775808` (الحد الأدنى لـbigint الموقّع) — صحيح SQL، ومثبت في `08_fin07_numeric_boundaries_verification.sql`. لا صراع مع قاعدة الدقة (منزلتان) لأن الحافة قيمة قصوى مشفرة وليست كسرًا.
- **مدخلات عملاقة:** `calculateTripAmounts` يرفض `OUT_OF_RANGE` قبل تخصيص BigInt للمدخلات الضخمة (حد ٢٥٦ رقمًا) ويمنع إجمالي نقلة يتجاوز bigint — يطابق «لا حساب سحابي/تلاعب بالمعادلات» ويضيف حماية DoS رقمي. الحساب التقريبي D01 لم يتغير (الاختبارات الأصلية باقية).

### الافتتاحيات — `trip-cash-opening-validation.ts` + مسار الكتابة
- `writeDemoTrip` يتحقق من افتتاحي نقد الحساب المسؤول **قبل** تخصيص المعرف وأي تغيير حالة، وحراسة الشاشة وحدها لم تعد وسيلة الإنفاذ — يطابق قاعدة «الرفض يمنع الحفظ». رفض نقلة تسبق افتتاحي الحساب (FIN-03) معتمد ضمن نطاق الدفعات النقدية لكل (عربية + مسؤول).

- **قرار غير محسوم مسجّل:** إدخال نقلة بتاريخ داخل نطاق افتتاحي نقد موجود **لفرق شغل المقاول** لم يُمس هنا (افتتاحي فرق الشغل قراءة فقط كما في H044)؛ لا افتراض جديد. لا داعي لقرار إضافي.

## ٦) هل يعمل الاختبار الجديد `cash-movement-label-validation` ضمن الفحوص الآلية؟

**لا. النتيجة: غير موصول.** الدليل (قراءة مباشرة على `caac3149`):

- `git grep "cash-movement-label" caac3149` ⇒ يظهر فقط في تقرير CASH-LABEL-01 وISSUES، **لا في `verify.yml`**.
- خطوات Vitest في `verify.yml` تعمل ملفات محددة بالاسم (`npx vitest run <file>`)، و`cash-movement-label-validation.test.ts` ليس منها.
- `npm run check` = `typecheck --workspaces && npm run test --workspaces --if-present`؛ `apps/web/package.json` **ليس فيه سكربت `test`** ⇒ الحزمة تُتخطى، والاختبار لا يُشغَّل.
- إعدادات Playwright تشغّل `e2e/*.spec.ts` في جذر المستودع فقط، والملف اختبار Vitest في `apps/web/e2e/`.

**الأثر:** سلوك الإصلاح نفسه مُتحقق منه آليًا عبر `vehicle-cash-report-validation.test.ts` و`e2e/vehicle-cash.spec.ts` (كلاهما ضمن الـRun الأخضر، وصُحّحت تأكيداتهما لتثبت المعرف وتنفي الإيصال — تقوية لا إضعاف). نتائج 3/3 للملف الجديد منقولة من تقرير المنفذ (RED ثم GREEN) ولم أستطع إثبات تشغيله آليًا. **التوصية:** إضافة سطر `npx vitest run apps/web/e2e/cash-movement-label-validation.test.ts` في `verify.yml` (أو دمجه في خطوة D16 الموجودة) قبل الدمج أو مباشرة بعده في متابعة صغيرة.
